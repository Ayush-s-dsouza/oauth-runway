# Decisions

One entry per real tradeoff: what was chosen, what was rejected, why, and what would overturn it. This is for auditing the reasoning later, not for evaluating the product — see README.md for that.

---

## 2026-10-28 — Three fixed gates instead of a single difficulty score

**Decision:** Every guide is organized around three stages (works for you / works for test users / works for anyone), each separately marked as review-required or not, instead of one difficulty label or a free-form writeup.

**Alternatives rejected:**
- A single score like "Medium difficulty" — fastest to build, but collapses the one fact that matters most: almost every provider lets you build *today*, and only the "anyone" stage makes you wait. A single score can't say that.
- Free-form prose guidance — flexible, but not scannable, not checklist-able, and not comparable across 100 different apps.

**Why:** The developer's real question is "how far can I get before I'm stuck waiting on someone else," not "is this hard." The gate structure answers that directly, and gives every provider the same shape, which is what makes 100 guides read as one product instead of 100 one-off essays.

**What would change my mind:** If a provider's real process doesn't map onto three stages (no dev/test distinction at all), the schema needs a variable-length or "not applicable" gate. None of the 6 curated apps forced this, but it's worth checking again around guide #20-30.

## 2026-10-28 — HTTP probes instead of browser automation

**Decision:** The agent's "do real investigation" tool is guarded raw HTTP requests (probe_url, probe_oauth_authorize, probe_oidc_discovery), not a headless browser.

**Alternatives rejected:**
- Playwright driving real signup flows, like the related `credforge` project does — it works, but only for a small hand-registered set of vendors, because it breaks on logins, CAPTCHAs and JS-only forms, and needs real credentials to go further than that.

**Why:** The useful fact — "does this endpoint exist, and how does it validate an unknown client" — doesn't need a browser. `probe_oauth_authorize` sends a deliberately invalid `client_id` to the live authorize endpoint and reads back the real response (e.g. Google's decoded `invalid_client` error, Shopify's per-store 404). That's genuine interaction with live provider infrastructure, without the fragility of driving a UI.

**What would change my mind:** If the bar is "get further into the actual flow" (e.g. a filled consent screen), that needs credentials or a browser — a materially heavier scope than this assignment's time budget.

## 2026-10-28 — Deterministic post-hoc validator instead of trusting the model's self-report

**Decision:** After the agent submits a guide, plain code (`validate.py`) re-checks every cited URL against what was actually fetched during that run and downgrades anything unconfirmed to "inferred." The model is never allowed to self-label a claim "tested."

**Alternatives rejected:**
- Trust the model's own evidence labels — simplest, but exactly the failure mode the assignment's "sound judgment about evidence" criterion is probing for (a model citing a URL it recalled rather than fetched).
- A second LLM call as a judge — plausible, but non-deterministic, and still needs trusting. A code-level check against the actual tool-call log is strictly more reliable for this specific error class.

**Why:** This check doesn't depend on model quality at all — it's matching against a log of what was really retrieved, not asking anything to reflect. It's the one piece of the design that should behave identically on any model.

**What would change my mind:** Nothing yet. This is the part of the system I'd defend hardest.

## 2026-10-28 — Six hand-researched curated guides instead of six agent-generated ones (interim)

**Decision:** The library's 6 guides were written by me, reading provider docs directly, not generated by the live agent. Each is labeled "source-checked, not yet hand-tested."

**Alternatives rejected:**
- Block all progress until a working Anthropic API key existed.
- Generate the 6 with the agent anyway and present them as final.

**Why:** No valid key was available during the build window — both keys found in related projects were revoked. Writing the guides from primary sources, using the same evidence-tagging schema the agent itself uses, keeps the output honest and gives `scripts/compare.py` something real to diff the agent's version against once a key exists.

**What would change my mind:** This is explicitly provisional. Once a key exists, the agent should generate its own version of these 6, and `scripts/compare.py` becomes the actual "check a sample of the guidance" deliverable the assignment asks for — not just a script sitting unused.

## 2026-10-28 — Tuned against one model (Opus 5.5), not validated across model tiers — open risk

> **Superseded** by the two-tier routing entry below. Kept for the reasoning trail.

**Decision:** Build and tune the whole system against `claude-opus-5-5` only.

**Alternatives rejected:**
- Validate against a weaker model (e.g. Haiku) up front, to separate what the schema/tools/validator contribute from what the model's own capability contributes.

**Why:** Time budget didn't allow a second full research-and-generation pass against a second model, and the assignment doesn't require multi-model robustness.

**The actual risk, named plainly:** if the system works well mainly because Opus 5.5 is a capable model, and the schema/tool-forcing/validator contribute little beyond that, the engineering story is weak — the merit belongs to the model, not the harness. I don't currently know which of these is true.

**What would resolve it (cheap, no code changes needed):** `AGENT_MODEL` is already an env var (`app/agent.py`), so this is pure API spend, not new code:
1. Run the same harness on 1-2 apps with `AGENT_MODEL=claude-haiku-5-5` vs. the Opus default.
2. Run a bare-prompt baseline (no schema, no tools, just "research OAuth setup for X") on both models.
3. Compare. If the harnessed Haiku run closes most of the gap to harnessed Opus, the scaffolding (forced structure, forced tool use before answering, the deterministic validator) is doing real, model-independent work. If harnessed Haiku is still far behind harnessed Opus, the honest conclusion is that the harness mainly buys reliability and evidence-tracking, while synthesis quality stays capability-bound — which is still a real result, just a more modest one.

Report whichever result comes out. Neither should be hidden.

## 2026-10-28 — Two-tier model routing, decided in code: cheap model researches, strong model synthesizes

**Decision:** Split the single agent loop into two phases with different models, always, with no switch exposed to the person using the product:
- **Research** (`RESEARCH_MODEL`, default `claude-haiku-5-5`): the tool loop (search, fetch, probes, Composio lookup). Its only output is `compile_findings`: cited facts, with no gate structure, verdict or step ownership.
- **Synthesis** (`SYNTHESIS_MODEL`, default `claude-opus-5-5`): no tools. Builds the guide only from the findings, and must reuse their ids as evidence.
- **Escalation:** if research doesn't converge within its turn budget, it is retried once on the synthesis model. The guide's provenance records that it escalated and why.

**Alternatives rejected:**
- *One model for everything* (the previous design). Every token, mostly spent reading fetched pages, is billed at the top rate. There's also no way to tell which steps actually need the capability.
- *Let the user pick a model per request.* This pushes an engineering decision onto someone who can't make it well, and was explicitly ruled out.
- *Escalate on output quality* (e.g. too many unsupported claims). This needs a validated threshold, and none exists yet. Stall detection is the only trigger that doesn't rest on a guess.
- *A middle Sonnet tier for research.* It may turn out right, but the instruction is to push work down as far as quality allows. So start at the cheapest tier and move up only when the eval says so.

**Why split exactly here:** pulling a cited fact out of a page is narrow and well-specified, which suits a cheap model. Deciding that "HubSpot's real constraint is the 25-install cap, not the review" means reasoning across several findings, which is where capability shows. The split also forces compression at the boundary: synthesis never sees raw HTML, only cited findings. And because synthesis has no tools, every claim in the final guide traces back to something research actually retrieved.

**What would change my mind (the eval in `eval/` measures exactly this):**
- `v2` (Haiku→Haiku) matches baseline on key-fact recall and groundedness → move synthesis to Haiku too.
- Baseline (Haiku→Opus) is clearly worse than `v1` (Opus→Opus) on recall, or escalation fires often → research needs a stronger model. Try Sonnet before Opus.
- Synthesis keeps dropping findings it was given (low recall even though research found the fact) → the hand-off format is losing information, and the schema needs work before any model change.

## 2026-10-28 — Eval design: atomic facts as the headline, a judge outside the models under test, infra failures never scored

**Decision:**
- Grade generated guides on **key-fact recall** for 6 reference apps, judged by Sonnet 5.5.
- Add free programmatic checks on every case. "Composio managed?" is checked against the live Composio API.
- Add a quote-support judge to catch real URLs with made-up content.
- Run three routing variants so the routing decision is measured rather than assumed.

**Alternatives rejected:**
- *Scoring how the guide divides the three stages* (does Slack's public distribution belong in stage 2 or 3?). Valid guides divide stages differently, so this would penalise correct structures.
- *A holistic 1–10 quality score.* Vague, unreproducible, and prone to rewarding length.
- *Exact match on timelines.* Free text with many correct phrasings.
- *Opus as judge.* It is the synthesis model under test and wrote the answer key: maximum self-preference. *Haiku as judge* has the same problem on the research side.
- *Scoring timeouts and API errors as 0.* That would blame the model for the plumbing.

**Why:** atomic facts are checkable: "states the 25-install cap" is yes or no, where "good guide" is a matter of opinion. Fact recall is also the property that matters to a developer: did the guide catch the thing that will block me?

**Known weaknesses (logged, not hidden):**
- The answer key is model-authored, from the curated guides. Each fact traces to a fetched source, but none is human-verified.
- 25 facts across 6 apps gives coarse resolution, roughly ±10–15 points.
- The famous apps are partly answerable from memory.
- The judge hasn't been calibrated against human grades yet.

**What would change my mind:** if the judge disagrees with a human on more than about 1 in 10 of a hand-graded sample, fix the judge prompt before trusting any comparison. If baseline and v1 differ by less than the noise floor, add reps on the reference slice before deciding anything.

## 2026-10-28 — Steer the cheap research model with a coverage gate in code, not a bigger model or a stronger prompt

**Context (measured, not assumed):** on the first live eval, Haiku research scored 0.74 key-fact recall against 0.93 for Opus research. Traces showed the cause: Haiku read a median of 4 pages vs 14 and never found facts that live on specific docs pages. The prompt already asked for 6–10 page reads; Haiku ignored it.

**Decision:** add a deterministic gate on `compile_findings`. Findings are accepted only if:
- at least 6 pages were actually fetched, and
- test-user limits, public-launch review, scopes and requirements each have a finding sourced from a page that was actually fetched, not a search snippet.

Otherwise the findings go back to the model with a specific list of what's missing, at most twice. The gate is off by default until `v3`/`v4` show it helps.

**Alternatives rejected:**
- *Move research to Opus.* That works (0.93), but costs 2.7× per guide and gives up on the goal of pushing work to the cheapest model the harness can steer.
- *Move research to Sonnet.* A reasonable fallback, but it still swaps a model for what the traces show is a steering problem. Try harness steering first.
- *A stronger prompt.* The prompt already states the budget and Haiku doesn't follow it. A code check is the only lever that doesn't depend on the model choosing to comply.
- *Escalate to Opus when coverage is thin.* That's a stronger version of today's stall escalation, and the next step if the gate alone doesn't close the gap.

**What would change my mind:**
- If `v3` doesn't close most of the gap to `v1`, escalate thin research to a stronger model instead of bouncing it.
- If `v4` (all Haiku + gate) matches `v3`, writing can move to Haiku too. Writing is about 85% of the default setup's cost, so that would be the bigger saving.
- If the gate fires on providers that genuinely lack a topic, loosen it so that an open question explaining what was checked counts as coverage.

## 2026-10-29 — The harness supplies the research plan; code owns the evidence

**Context (measured):**
- With the coverage gate, Haiku read more pages but still ran only 2–4 searches, so it never found changelog pages. That's where recent limits are announced: HubSpot's install cap, Slack's non-Marketplace rate limits.
- Separately, a Haiku writer invented 16–23% of its evidence and altered quotes, despite being told not to.

**Decisions:**
1. **Research plan** (`RESEARCH_PLAN`). The code puts 5 searches in the research brief: install/user limits, the developer changelog, listing review, sensitive scopes, app creation. The gate then requires at least 4 searches to have run.
2. **Evidence lock** (`EVIDENCE_LOCK`). After writing, code rebuilds the evidence list from research findings by id. Unknown ids are dropped, and the claims they propped up become "unsourced". The quote, URL and status are always the researcher's, word for word.

**Alternatives rejected:**
- *Ask the model for more searches and to cite only findings.* The prompt already said both; a cheap model doesn't comply reliably.
- *A third model call to audit the evidence.* More cost and more non-determinism, for a check that code can do exactly.
- *Changing the synthesis prompt for the locked variants.* I kept prompts identical across variants so the lock is the only difference being measured.

**Result:**
- The plan fixed HubSpot (0.5 → 0.92–1.0).
- The lock eliminated fabrication. It also exposed that v4's "99% sourced" was really 82%.
- But the full lock also stopped Opus from tightening research's overreaching claims: quote support fell from 0.67 to 0.57. So `EVIDENCE_LOCK=quote` locks quotes, URLs and status while letting the writer reword the claim. That's v7.

## 2026-10-29 — Routing recommendation: Haiku researches (steered), Opus writes

> **Finalised by v7** (see the entry below): shipped with the quote-only lock.

**Decision (pending v7's lock mode):**
- Research on Haiku with the gate and the research plan.
- Writing on Opus with the evidence lock.
- In the eval (v6): key-fact recall 0.91 against 0.93 for all-Opus (paired difference −0.02, within noise), at $0.37 per guide against $0.85, and faster.

**Why not all-Haiku (v5, $0.09/guide)?** Recall is close (0.85), but the Haiku writer misjudges difficulty (error 0.67 vs 0.17–0.33) and invents evidence that the lock then has to strip, leaving 18% of steps unsourced. Difficulty judgement and faithful writing are the capability-bound part; no steering moved them.

**Why not all-Opus (v1)?** The research half costs 2.3× as much for no measurable recall gain once Haiku is steered.

**What would change my mind:**
- A cheaper writer (Sonnet 5.5) matching Opus on difficulty judgement and invention rate. That's the next variant worth running, since writing is about 85% of v6's cost.
- A human-verified answer key moving the numbers.
- A larger case set showing the v6-vs-v1 gap is real.

## 2026-10-29 — Shipped default: v7 (Haiku research + gate + plan → Opus writing + quote-only lock)

**Decision:** the app's defaults are now `RESEARCH_MODEL=claude-haiku-5-5`, `SYNTHESIS_MODEL=claude-opus-5-5`, `COVERAGE_GATE=1`, `RESEARCH_PLAN=1`, `EVIDENCE_LOCK=quote`. Earlier eval variants pin their own switches, so their results stay reproducible.

**Evidence, on the same 5 reference apps:** v7 against all-Opus (v1):
- key-fact recall 0.88 vs 0.92 (within noise)
- quote support **0.71 vs 0.64**
- steps sourced 1.00 vs 0.98
- **$0.40 vs $0.89** per guide

Against v6 (full lock), the quote-only lock improved quote support on every app (+0.12 on average) at no cost to recall.

**What the harness does that the model can't be trusted to:**
- read enough pages (gate)
- search where recent limits live (plan)
- never invent evidence or alter a quote (lock)

**What still needs the strong model:**
- judging difficulty
- rewording claims to fit their quotes

**What would change my mind:**
- A Sonnet-writer variant matching v7. Writing is about 85% of v7's cost, so that is the next saving to test.
- A human-verified answer key, or a larger case set, separating v7 from v1.
